# source 模式协议（取材 / 采集）

> **一句话**：人给一份**索引**（课题清单 / 待深入方向钩子），Agent **动用全部取材通道** fan-out 搜集原始材料，整合成结构化原始笔记**落 `Inbox/raw/`**，标 `source` + 采集日期——**到此为止，不 ingest**。

## 它在管道里的位置

`source` 站在编译生命周期的 **②研究发散** 这一相，是整条管道的**最前端**：

```
①发散提问(Inbox 散文)
   ↓
② source ← 本模式：索引 → fan-out 取材 → 落 Inbox/raw   ← 守 ingest 闸，不碰 wiki
   ↓
③ ingest（人/单独命令把闸）→ wiki 本体
```

**与 deep-dive 的区别（方向相反，别混）**：

| | 驱动源 | 方向 | 收口 |
|---|---|---|---|
| **deep-dive** | `lint(Coverage)` 自动找 wiki 内部缺口 | wiki 内向：缺口 → 填 | 直接 ingest 进 wiki |
| **source** | **人给的索引/钩子清单** | 向外界 fan-out 取材 | **落 Inbox/raw，停在闸前** |

deep-dive 是「wiki 知道自己缺什么，去补」；source 是「人指了一串方向，去外面把原料搜回来堆好」。source 的产出**正是 deep-dive/ingest 的输入**。

## 为什么收口在 Inbox/raw 而不是直接进 wiki

守库的不变量：**捕获免费、晋升收紧**；**ingest 是把闸的编译步**（去重/6 档时间表/退役协议/schema 校验）。source 只负责把**原料**搜回来堆在闸前，**晋升进正典的判断留给 ingest**（人在场把关或单独命令）。这样：
- 取材可以激进、广撒网、容忍噪声；编译仍然严谨。
- 原料带完整溯源躺在 `Inbox/raw/`，随时可 `/auto-wiki ingest` 或 `/digest-inbox`。

## 输入：什么算「索引」

任意一份**钩子清单**，常见三种：
1. **某篇 `Inbox/raw/` 笔记末尾的「待深入方向」**（最典型）。
2. **用户当场给的课题列表**（「帮我把这几条都去找找资料」）。
3. **一篇散文里散落的待证实钩子**（Agent 先抽成清单，请用户确认再取材）。

## 执行流程

### Phase 0 — 路由：每条钩子命中到域

先读 `wiki/_index.md` 注册表；若实例存在 `{ops_dir}/onboarding.md`（路径由 `python <skill>/references/instance.py .` 解析），同时读取其中的真实工作流、动态更新节奏和数据/合规边界。把索引里**每条钩子**按关键词命中到**域**（库若声明了方向 direction，一并命中）。命中决定走哪组取材通道——**通道分组按库配置，见库内 CLAUDE.md「取材通道」节**。横跨多域的钩子双路取材；不得为了完成取材绕过实例声明的联网、出机或脱敏限制。

### Phase 1 — 拆索引为原子查询

把索引拆成 N 条**具体、可检索**的 atomic query。一条模糊钩子拆成 2-3 条原子查询（例：「X 技术延迟对 A/B 公司的影响」→ ① X 商用时间表最新预测 ② A 公司相关订单/份额 ③ B 公司路线表态）。**列出拆解结果，让用户过目可增删**（防止把方向理解偏）。

### Phase 2 — fan-out 多通道取材

**动用全部工具**，按钩子命中选通道并行检索（能 batch 就 batch）：

**取材通道按库配置：见库内 CLAUDE.md「取材通道」节**（通道分组、batch 用法、黑名单）。库未配置时用通用通道兜底：WebSearch / WebFetch、通用搜索工具的 batch 检索、长网页阅读工具。

并行纪律：
- **同方向多题优先 batch**（用支持 batch 的检索通道一发多查），延迟≈单发。
- 一条原子查询尽量**交叉 2+ 通道**（专业源 + 公开网页 / 一手 + 二手），便于互证。
- **数值/行情走数据源工具**，别让 LLM 凭记忆填数。

### Phase 3 — 收口整合（每条原子查询一段）

每条原子查询整合成一个条目：
- **发现**：2-5 句要点，带关键数字（数字必须有来源）。
- **溯源**：`标题 + 机构/作者 + 日期 + 链接`。**链接会过期，溯源以「标题+机构+日期」为准**。
- **渠道与可信度档**：`[一手]` / `[二手·权威]`(官方/头部专业机构) / `[二手]`(自媒体，标黑名单则跳过)。**库特有分档**（附加档位与纪律）见库内 CLAUDE.md「取材通道」节。
- **存疑/分歧**：多源冲突时并列，标 `contested`，**不在 source 阶段裁决**（留给 ingest）。

### Phase 4 — 落 Inbox/raw

两种落法，二选一：
- **追加**：索引本就来自某篇 `Inbox/raw/` 笔记 → 取材结果**追加到同一篇**的「## 取材产出（{采集日期}）」章节下，原钩子保留。
- **新建**：索引是用户当场给的 → 新建 `Inbox/raw/{采集日期}-{slug}-取材.md`。

frontmatter 必填：
```yaml
---
tags: [inbox, raw, <方向>, <主题>]
type: capture
direction: <库配置的方向（若库声明了 direction）>
compiled: false          # 守闸：未编译
created: <采集日期>
source: source 模式 fan-out 取材
取材通道: [<实际动用的通道>, ...]
索引来源: <钩子来自哪篇/哪次对话>
---
```

### Phase 5 — 报告

```
source 取材完成（索引：{N} 条钩子 → {M} 条原子查询）
- 落点：Inbox/raw/{文件}（compiled: false，守 ingest 闸）
- 命中域：{方向/域}
- 动用通道：{列出实际调用的工具}
- 每条钩子产出：
  · 钩子1 → 找到 {k} 条材料（{一手/二手·权威 数量}）
  · 钩子2 → 找到 {k} 条；其中 1 处分歧已标 contested
  · 钩子3 → 缺口：未找到一手数据，建议 {下一步}
- 够 ingest 的：{列出哪几条材料密度足够，可直接 /auto-wiki ingest}
- 仍缺的：{列出缺口}
```

## 纪律清单

- **不碰 wiki**：source 永不写 `wiki/`、永不动 `data.db`。晋升进正典是 ingest 的事。
- **溯源不可省**：每条材料记「标题+机构/作者+日期」，链接仅作便利。
- **渠道分档**：一手 > 二手·权威 > 二手；自媒体黑名单渠道跳过；**库特有分档纪律见库内 CLAUDE.md「取材通道」节**。
- **数值走数据源工具**：不凭记忆填数。
- **不裁决分歧**：多源冲突并列标 `contested`，裁决留给 ingest。
- **拆解可审**：Phase 1 的原子查询拆解列给用户过目，防止取材方向跑偏。
- **无人值守模式**：若在定时任务/无人值守驱动器下跑，产出一律落 `Inbox/raw/`（本就如此），高危晋升（newnode/xedge）一概不做——本模式天然只投递候选，符合「产出收口」原则。

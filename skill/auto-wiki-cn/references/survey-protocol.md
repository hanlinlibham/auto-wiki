# survey 模式协议（存量勘察）

> **一句话**：人指一个**已经存在的**笔记库/工作目录，Agent **只读结构不读正文**地扫一遍，反推出 init 提案草案与种子草案，**到此为止——不建库、不写用户任何文件**。

## 它在管道里的位置

`survey` 站在 `init` **之前**，是冷启动的取证相：

```
① 用户已有的存量（Obsidian 库 / 笔记文件夹 / 工作目录）
   ↓
② survey ← 本模式：扫结构 → 反推提案 → 问出禁混规则   ← 守 init 闸，不建库
   ↓
③ init（人确认提案）→ 建库
```

**为什么需要它**：`init` 第一轮要从一句口头回答里推导八样东西（领域 slug、Hub 名、中心对象、4–6 个节点类型、5–12 个路由词、种子选择、3–10 个回归问题、vault 名）。人冷着答这个，给的多半是场面话——"我想把研究资料管起来"。而他已有的笔记库**早就把答案写在结构里了**：目录名是他的分类学，文件名高频词是他的路由词，改动时间分布告诉你什么是动态知识。

问「你会反复问哪三个问题」，人答不出；问「我看你这儿有 40 篇跟转债有关的，你平时问它们什么」，人张口就来。

**与 source 的区别（都不写正典，但源头相反）**：

| | 驱动源 | 读什么 | 收口 |
|---|---|---|---|
| **source** | 人给的索引/钩子 | **外部世界**的新材料 | 落 `Inbox/raw/`，停在 ingest 闸前 |
| **survey** | 人指的已有目录 | **用户自己的存量，只读结构** | 只出报告与提案草案，**一个字节都不落盘到用户库** |

## 三条硬边界

**一、不读正文（默认）。** 只读目录名、文件名、扩展名、修改时间。用户的存量里可能有客户材料、内幕信息、私人日记——零内容暴露，他才敢让你扫。要读正文必须**逐次授权**，且只读用户点名的那几个文件。`--frontmatter` 开关只读 YAML 头的键与标签，也要先说明再开。

**二、不导入存量。** `init-protocol.md` 第一条边界写着「不导入整批历史资料」。survey 不破这条：**读结构不是导入**。扫完之后要不要把存量编译进库，是之后 `ingest` 的事，一次一批，人把闸。

**三、不写用户的库。** survey 的产出只交给用户看，或写进**新建的**知识库目录。绝不在用户既有的笔记文件夹里创建、修改、移动任何文件。

## 上下文纪律：分层勘察，别一次灌满

存量库动辄上万文件。**一次性把全库扫进上下文，就没有下一步了**——后面的访谈、提案、起草全都没预算了。

- **第一遍只扫顶层，出一页摘要。** `survey.py` 所有分节都按 `--top` 截断，**输出长度不随语料规模增长**：扫 100 个文件和扫 10 万个文件，报告都是一页。
- **绝不打印文件清单。** 只要聚合量（计数、频次、分布）。想看某个分支有什么，对**那一个子目录**重跑脚本，不要把全库拉进来再在上下文里筛。
- **下钻要用户点名。** 「这几个目录里哪个是你主要在用的？」——只对他点的那个下钻，一次一个。
- **计数不许自己数。** 数字一律取 `survey.py` 的输出。Agent 目测文件数必然出错，而错的计数会让整份提案失去可信度。
- 语料超过 3000 个文件时脚本会主动提示收窄。

## 执行流程

### Phase 0 — 圈范围，先说纪律

请用户指定要勘察的目录（可多个），然后**主动申明**将读什么、不读什么：

> 我只看目录名、文件名和修改时间，不打开任何文件。要看内容会先问你。

用户没圈范围时不要自作主张往上层目录走，更不要扫用户主目录。

### Phase 1 — 机器扫描

```bash
python <skill>/references/survey.py <目录> [--frontmatter] [--top 30]
```

Obsidian 库或已有 frontmatter 习惯的库加 `--frontmatter`（先征得同意）；只想要一页速览用 `--top 12`。

### Phase 2 — 反推候选（语义判断，Agent 做）

把扫描结果映射成 `init` 第一轮要的东西：

| 扫描结果 | 反推出 |
|---|---|
| 目录结构 | 用户自己的分类学 → **节点类型候选**（4–6 个，别照搬全部目录） |
| 文件名高频词 | **路由关键词**（5–12 个） |
| 反复出现的专名 | **中心对象**与实体清单 |
| 近 30 天改动集中的部分 | **动态知识**（要定期更新的） |
| 一年以上没动的 | **稳定知识**，或已经废弃 |
| frontmatter 键与标签 | 用户已有的元数据习惯，尽量沿用而不是另起一套 |

**必须过滤**：脚手架噪声（`README`、`index`、`草稿`、工具生成的中间文件）会混进高频词，它们不是领域术语。拿不准就把候选列给用户勾选，别自作主张。

### Phase 3 — 问出禁混规则（机器挖不到，只能问人）

结构能反推术语和分类，**唯独禁混规则挖不出来**——产物是收敛之后的结果，混淆的痕迹早被抹掉了。一个人笔记里写着「受托人」，你看不出他三年前把机构和角色搞混过。

问这一句：

> **你带新人的时候，反复纠正过哪几组概念？**

这比问「你们领域有哪些容易混的概念」好答十倍：前者具体、有情绪，教过新人的人有一肚子话；后者抽象，答不出来。

对每一组追问一句「混了会怎样」——后果才决定这条规则值不值得进种子。采到 3 组以上就够起草了，采不到就跳过，种子留空比编造好。

### Phase 4 — 三份产出

都只给用户看，不落进他的既有目录：

1. **勘察报告** —— 扫到了什么，一页。
2. **init 提案草案** —— 按 `init-protocol.md` 的十行提案格式填好，标注每一项**是从哪条扫描结果推来的**，让用户能核对而不是盲签。
3. **种子草案**（采到禁混规则时）—— 按 `seeds/` 格式起草，含标准术语、分类、关系模板、禁混规则四节。

### Phase 5 — 交接

问「按这个跑 init 吗？」。用户改哪项就只重列哪项。确认后转入 `init`，**跳过第一轮访谈**（提案已经有了），仍然要走第二轮（第一份材料与更新节奏）和第三轮（查看器与数据边界）。

## 纪律清单

- **不读正文**——默认零内容暴露；要读须逐次授权、只读点名文件。
- **不写用户既有目录**——一个字节都不写。
- **不导入存量**——守 `init` 第一条边界；存量入库走后续 `ingest`，人把闸。
- **不自己数数**——计数一律来自 `survey.py`。
- **不一次扫全库**——分层勘察，下钻按用户点名，一次一个分支。
- **不擅自扩大范围**——用户圈哪儿扫哪儿，不往上层走。
- **禁混规则只能来自人**——不从结构里编。
- **提案要可核对**——每项标出推导依据，不让用户盲签。

# Query 协议

> 基于 wiki 积累回答问题。不是 RAG——不搜原始文档，搜编译后的 wiki 页面。

## 流程

```
1. 理解问题
   ├─ 识别目标 wiki（从问题内容推断，或用户指定）
   ├─ 提取关键词（实体名、概念名、时间范围）
   └─ 判断问题类型（事实查询 / 比较分析 / 趋势判断 / 开放探索）

2. 搜索 wiki
   ├─ 读 hub（{主题中文名}.md）**只为定位类型**，再读对应 {类型}/_index.md 匹配标题与描述
   ├─ 读取匹配的页面（通常 3-8 个）
   ├─ 如果页面中有 [[wikilink]]，沿链接读取关联页面（一层展开）
   └─ 注意 confidence 字段：contested 页面需要特别标注

3. 综合回答
   ├─ 基于读取的页面内容综合分析
   ├─ 每个关键论点标注来源页面：[[page-slug]]
   ├─ 如果涉及 contested 信息，明确说明：
   │   "关于 XX，wiki 中存在矛盾：来源 A 说...，来源 B 说..."
   └─ 如果信息不足，明确说明缺口并建议 ingest 方向，
       同时按下方「query-miss 登记」在 {ops_dir}/query-miss.md 记一行

4. 可选归档
   ├─ 如果回答中包含有价值的新分析（不是简单复述页面内容）
   ├─ 提示用户："这个分析要归档到 wiki 吗？"
   └─ 用户同意 → 写入 analyses/{slug}.md，跑 regen_index.py 重建索引
```

## 回答格式

### 事实查询

```
根据 wiki 中 {N} 篇源文件的积累：

{直接回答}

来源：[[page-1]]、[[page-2]]
```

### 比较分析

```
基于 wiki 中的记录，{A} 和 {B} 的对比：

| 维度 | {A} | {B} |
|------|-----|-----|
| ... | ... | ... |

来源：[[page-1]]、[[page-2]]、[[page-3]]

注：关于 XX 维度，wiki 中数据有限（仅 1 篇来源），建议补充。
```

### 信息不足

```
wiki 中关于 {主题} 的信息不足：
- 相关页面：{N} 个
- 源文件：{N} 篇
- 缺口：{具体缺什么}

建议 ingest：
- {建议补充的材料类型 1}
- {建议补充的材料类型 2}
```

## query-miss 登记（0.4.0 新增：误拒侧唯一观测点）

「信息不足」分支触发时（query 与 recall 模式皆同），除了向用户报告缺口，**必须**在库的
`{ops_dir}/query-miss.md` 追加一行（文件/目录不存在则创建，**任何实例都不跳过**）。
ops_dir 不要猜：跑 `python references/instance.py .` 取 `ops_dir` 字段
（陋居范式库自动识别为 `08-Ops`，standalone 实例默认 `wiki/_ops`，可在实例配置里显式指定）：

```
- {YYYY-MM-DD} | {domain} | {问题的一句话摘要} | {miss类型} | 建议:{ingest 方向}
```

miss 类型四选一：`no_node`（缺页面）/ `no_edge`（页面在但关系断）/ `no_data`（缺数据点）/ `stale`（有但过时）。

**为什么必须记**：检索质量 = 误放 + 误拒两侧；巡检仪表（陋居范式的 patrol，或任何未来消费者）
只看得见登记过的误拒——它数的就是这个文件的行数。漏记 = 误拒侧永远为 0 = 供给侧一切粒度/召回优化失去目标函数。
这也是「秩维粒度框架」解析层的启用判据之一：query-miss 无数据之前，最优节点数的数学都在空转。

## 跨 Wiki 查询

当问题涉及多个 wiki 时：

1. 列出 `wiki/` 下所有 wiki 目录
2. 读取每个可能相关的 wiki 的 hub 页面（导航用；清单在类型子索引，不整读）
3. 分别搜索
4. 综合回答时标注来源属于哪个 wiki：

```
综合 enterprise-annuity wiki 和 charlie-munger wiki 的内容：

{分析}

来源：
- enterprise-annuity: [[alpha-corp]]、[[fiduciary-responsibility]]
- charlie-munger: [[circle-of-competence]]、[[margin-of-safety]]
```

## 查询性能

| Wiki 规模 | 查询策略 | 预期延迟 |
|-----------|---------|---------|
| < 30 页 | 读 hub + 相关类型 `_index.md` + 直接读匹配页面 | 快（< 5s） |
| 30-150 页 | 读 hub 定位类型 + 只读该类型 `_index.md` + grep + 读 top 匹配 | 中（5-15s） |
| 150-500 页 | 同上；**只读命中类型的子索引**，不跨类型整读 | 慢（15-30s） |
| > 500 页 | `fts_index.py search` 拿 top-N 再精读，不读清单 | 稳定（与库大小无关） |
| > 500 页 | 超出 Skill 设计范围 | 建议迁移到平台 |
